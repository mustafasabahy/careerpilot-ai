# Evidence-linked career preparation — Phase 6

Run `uv run --locked careerpilot-prepare` for synthetic, offline preparation.
Use `--scenario missing-profile` or `--scenario conflicting-dates` to inspect
insufficient-data paths. All demo databases are temporary. Checked-in examples in
`examples/preparation/` were generated by the actual workflow, including request,
result, original CV, new drafts, unified diffs, intelligence, and practice plan.

## Boundaries and contracts

`domain/career_intelligence.py` catalogs source facts and explains the existing
baseline assessment without I/O. `domain/preparation.py` validates fact references,
clarifications, practice plans and immutable preparation metadata.
`application/preparation.py` loads authorized references, reproduces the assessment,
coordinates the planner and persists validated drafts. `application/draft_generation.py`
validates fact selections and renders text. Provider construction stays in
`providers/factory.py`; adapters implement the application-owned DraftPlanner port.
`workflows/preparation.py` only orchestrates these operations. No new dependency,
agent, service or tool permission is introduced.

A PreparationRequest contains stable candidate, job and assessment IDs, a caller
request ID and UTC time, plus optional existing document/original-version IDs.
PreparationRecord links those objects to exactly one CV and one cover-letter
version. It snapshots rules, normalized criteria, explanations and fact provenance;
it records planner/model, renderer/prompt version and content hashes. Document
bodies remain DocumentVersion content, separate from metadata. Outputs are typed
`drafts_created`, `needs_information` or `error`; errors cannot masquerade as drafts.

The existing assessment must reproduce exactly under the injected criteria and
rules. Older assessments lack their rule context: supply the original definitions
and policy or validation fails. The new preparation snapshot retains that context.
Requirements unsupported by the deterministic baseline stay unknown; no invented
years-of-experience, qualification equivalence or hiring probability is added.

## Evidence and questions

Each requirement retains its hard/preference/unspecified classification, baseline
outcome, reason, explanation and applicable profile fact IDs. Those facts link to
source record/field and evidence locators. An explicit proficiency shortfall differs
from an absent skill or unverified assertion. Only user-statement evidence permits
a fact into generated prose. User confirmation is provenance, not independent proof
of competence; an authenticated future input boundary must establish its origin.

Missing identity or lack of any confirmed professional fact blocks drafts. Different
known end dates for the same role/start or education/start block generation and
prompt clarification. A missing end date is not contradictory; overlapping separate
jobs are not treated as dishonesty. Other missing history, unsupported requirements,
gaps and unverified facts produce targeted questions and can coexist with drafts.
Questions are returned for user review; applying answers/profile editing is deferred.
No nationality, age or other protected-trait inference is used.

Interview questions and three timed practice sessions derive from requirements and
existing evidence. Language practice appears only when a language criterion exists.
Questions ask the user for real examples; they do not supply invented achievements.

## Constrained generation and review

The planner selects/orders existing professional fact IDs only. Pydantic rejects
extra prose and deterministic membership checks reject fabricated/unverified IDs.
CV and cover-letter text uses exact source fact strings with controlled templates.
Job title/employer are labeled source text and JSON-escaped to prevent injected
newlines becoming candidate assertions. Source documents cannot grant permissions.
The default mock planner needs no network. The optional OpenAI planner reuses the
existing native strict structured-output integration, fixed endpoint, timeout,
retry/token limits and normalized provider errors; no tools are attached.

This deliberately produces conservative plain-text drafts, not stylistically free
LLM rewriting, a professionally designed CV, or an automatic claim verifier. Every
draft requires human review. Unsupported metrics and achievements cannot be added
by the model because no free-prose output field exists. An original CV is preserved
as raw source, never automatically promoted into confirmed facts.

Server-supplied PreparationAuthorization requires scoped READ_CANDIDATE/READ_JOB
access, an allowed job ID and explicit `allow_drafts=True`. Real model export also
requires `allow_profile_model_export=True`; the demo exposes the explicit
`--allow-profile-model-export` switch. Ordinary LLM environment settings alone do
not grant export. Only confirmed professional fact text/IDs and preferred IDs go
to the planner; names, work authorization, raw CVs and evidence locators do not.
Professional facts can still be personal data. Real calls incur provider costs;
see `llm-integration.md` for credentials, configuration and opt-in live tests.
Phase 6 tested the real adapter through in-memory HTTP simulation, not paid calls.

## Workflow and persistence

`inspect_evidence` validates request, authorization, references, assessment and
readiness. Its conditional edges select `clarify`, `replay`, `generate_plan` or
`fail`. `generate_plan` invokes the planner outside a database transaction;
`validate_plan` checks its output; `persist_drafts` renders and atomically stores
both document versions and PreparationRecord. Generation/validation failures route
to `fail`. Unexpected infrastructure failures propagate. Terminal patches clear
transient source context/proposals. The actual diagram is `examples/preparation/workflow.mmd`.
Tracing is disabled for execution/streaming; no external checkpoint store is used.

Selected existing documents append latest version + 1 with a predecessor and
reviewable unified diff. Otherwise new documents begin at version 1. The optional
original-CV pointer must belong to the same candidate/resume document. Source
versions remain byte-for-byte unchanged. Replaying a completed identical request
reuses its drafts without another planner call; changed input under the same ID
conflicts. Concurrent pending requests are not a distributed exactly-once billing
guarantee. All writes commit together or roll back, with foreign keys enforcing
candidate/job/assessment and document ownership. Hash checks detect inconsistent
stored content; this is not a tamper-proof ledger against direct database access.

Schema v2 adds `preparations` and a composite assessment key. Calling
`SQLiteDatabase.initialize()` atomically upgrades v1 to v2; historical v1 SQL and
existing JSON aggregates remain intact. Back up non-disposable development data
before upgrading. Unknown/unversioned schemas are rejected; downgrades are not
supported and old application versions reject v2. Migration rollback and original
CV preservation are tested. PostgreSQL remains deferred.

## Verification and API references

Run `sh scripts/check.sh` with uv available. Normal tests deny network access and
cover fabricated claims, malformed plans, missing fields, conflicting dates,
absent language requirements, authorization, routing, roundtrips, lineage,
idempotency, invalid references, migration and transaction rollback.
No submission, production authentication, profile-update flow or deployment exists.

The installed LangGraph 1.2.18 APIs use TypedDict StateGraph, partial node updates,
conditional edges, compile/invoke/stream and Mermaid export. Langchain-core 1.7.0
and langchain-openai 1.7.3 supply the existing model integration. Checked against
installed execution and official documentation:

- [LangGraph graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)
- [Direct model structured output](https://docs.langchain.com/oss/python/langchain/models#structured-output)
- [OpenAI integration](https://docs.langchain.com/oss/python/integrations/chat/openai)

The documentation evolves; the lockfile and executable adapter tests establish
which signatures this project actually uses.
