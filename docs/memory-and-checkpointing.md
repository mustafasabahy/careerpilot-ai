# Phase 7: memory, checkpoints and context

CareerPilot now has a small resumable career-context review workflow. It retrieves
explicitly confirmed memory references, pauses for human review and resumes into
an accepted or cancelled state. The earlier analysis, discovery, extraction and
preparation entry points retain their behavior. They are not silently checkpointed:
their transient state can contain full profile/document data. Preparation outputs
remain in authoritative business tables. This phase does not claim crash recovery
for those older graphs or automatic continuation from context review into drafting.

## What belongs where

| Location | Content | Authority and lifecycle |
| --- | --- | --- |
| Graph state | Owner/thread/candidate IDs, memory IDs (at most 20), memory revision, workflow version and review/completion flags | Coordination references only; never source facts or prose |
| Local checkpoint file | LangGraph super-step snapshots, pending writes, interrupt references and execution metadata | Short-term execution history; no user messages, CVs, memory text or model output |
| Dedicated memory database | Typed job/location/work-arrangement preferences, confirmed career facts, explicit corrections, career goals; revisions and thread ownership/tombstones | Explicit user-confirmed memory; current values only, separate from domain profile |
| Existing business SQLite v2 | Profiles, source evidence, jobs, assessments, preparation records, document versions and application/audit records | Authoritative business aggregates; unchanged by memory editing/deletion |
| Ephemeral BoundedContext | Selected current memories, requested confirmed profile facts, recent capped user/assistant/tool messages and omission accounting | Data only, no tool permission; summary is explicitly non-authoritative and never stored as memory |

`domain/memory.py` validates typed values. `application/memory.py` owns the repository
port and owner-bound operations. `persistence/memory_sqlite.py` implements durable
local memory and a thread registry; `persistence/checkpoints.py` manages official
LangGraph saver connections. `application/context.py` trims ephemeral context and
loads authorized profile facts on demand. `workflows/career_context.py` coordinates
review and exposes authorized state/history/resume/deletion. There is no agent,
embedding service, semantic search system or automatic fact extraction.

## Local execution and restart

```sh
uv sync --locked
uv run --locked careerpilot-memory
```

The default uses synthetic data and a temporary directory. It pauses, closes every
connection, constructs a new saver/graph, reads the saved state and resumes. Actual
sample output and Mermaid graph are in `examples/memory/`. Checkpoint IDs and
confirmation timestamps are generated by execution and will differ on another run.

For separate invocations with durable local files:

```sh
uv run --locked careerpilot-memory --directory work/memory-demo --action pause
uv run --locked careerpilot-memory --directory work/memory-demo --action state
uv run --locked careerpilot-memory --directory work/memory-demo --action history
uv run --locked careerpilot-memory --directory work/memory-demo --action resume
uv run --locked careerpilot-memory --directory work/memory-demo --action context
uv run --locked careerpilot-memory --directory work/memory-demo --action forget
```

The demo uses a fixed **synthetic** principal/thread, not a user authentication
mechanism. Reusing a completed/deleted ID to start another workflow is rejected;
use a new UUID via `--thread UUID` consistently across actions, or a new disposable
directory. `--action demo` expects a fresh directory. File paths are trusted operator
configuration, never LLM tool input. No key, model, network operation or .env is used.

Applications construct MemoryPrincipal only after authenticating the user and
establishing authorized candidate IDs, then inject CareerMemory and ContextBuilder.
A profile loader uses the existing business repository and must return the exact
requested candidate. The default has no profile loader and authorizes no candidate.
Never derive this principal from a model-produced ID or expose the underlying
repository/saver/compiled graph as a public API. There is still no HTTP auth layer.

## Checkpoint APIs and review behavior

The stable caller-supplied thread UUID is registered once with a server-bound owner
and optional authorized candidate. Every current/history/context/resume/delete
operation checks registry ownership. UUID unpredictability is not authorization.
Callers cannot select a checkpoint namespace, arbitrary checkpoint ID or a different
owner. History is read-only and bounded (default 20, maximum 100 snapshots); it is
not an editable time-travel API. No checkpoint is accepted after authorization is
revoked. Full saver internals and raw errors are not exposed by the state view.

The graph is START → review_context → finish → END. `review_context` calls
`interrupt()` with memory IDs/revision only. `Command(resume=True/False)` continues
the same thread. False cancels context use. Before resume or resolving context,
the service compares the current user's memory revision with the checkpoint.
Any preference edit, correction or deletion invalidates old context: start a new
thread and review again. Historical views retain references, never removed fact
text. The review acknowledges context selection only; it does not approve a CV,
submission, new fact or tool permission.

The wrapper uses `durability="sync"`, `get_state`, `get_state_history` and
`delete_thread` with the fixed thread configuration. Pending recoverable execution
can be retried via `invoke(None)`; unavailable/corrupt checkpoints fail closed.
Ownership commits before graph writes, so a failed start cannot let another user
adopt an orphan checkpoint. If a failure occurs before any usable state was saved,
delete that thread and start a new UUID. Graph shape/version changes require
explicit compatibility review; unsupported workflow-version markers are rejected.

## Long-term memory writes, corrections and deletion

`CareerMemory.confirm(MemoryWrite(...), explicitly_confirmed=True)` is a trusted
application operation, deliberately absent from LLM tools. Pydantic validates all
fields, rejects extra fields/owner assertions and requires user-statement evidence
for career facts. AI-inference and source-document-only evidence cannot become
confirmed career memory. A boolean alone cannot authenticate a user: a future UI/API
must actually obtain confirmation before invoking this operation. Arbitrary assistant
messages and summaries have no path that writes memory automatically.

Memory identities are namespaced by owner. Each owner has at most 100 items.
Creation uses expected_version=0; preference/goal changes supply the current
version. Concurrent stale updates fail with MemoryConflict. Existing career facts
must be changed through ExplicitCorrection, which references an owned fact's ID
and version, supplies a user-confirmed replacement and a reason. Correction and
retirement of the old fact occur in one transaction. Corrections can themselves be
corrected through a new correction. No old statement is copied into history, and
deleting a correction never resurrects the retired original.

`CareerMemory.delete(id, expected_version=...)` removes the current memory row and
increments the owner revision. `workflow.delete(thread)` commits an authorization
tombstone first, then removes all saver checkpoints/pending writes for that thread.
If physical purge fails, access remains denied and deletion can be retried.
`workflow.forget_all()` clears that user's memory, tombstones all their threads and
purges checkpoints; other users remain untouched. Minimal owner/revision and thread
UUID tombstones remain to prevent deleted IDs being adopted or recycled. Purge
errors propagate; callers must not report physical deletion until retries succeed.

These are logical application deletions, not forensic secure erasure of SQLite
pages, WAL files or external backups. Files are plaintext local development data;
manage file permissions and backup retention separately. Memory deletion does not
rewrite independent profile evidence, assessments, historical CVs or application
audit records. Correcting/deleting those business records requires a separate
explicit business operation (profile editing/whole-account erasure is not implemented).
This policy prevents memory changes silently modifying verified candidate facts.

## Context bounds and retrieval

Select memories deterministically by typed kinds and count; no arbitrary SQL,
filesystem path, URL or cross-user namespace is accepted. ProfileContextSelection
retrieves requested fact IDs/kinds on demand; only user-confirmed facts are eligible,
work-authorization facts are excluded, and no memory is silently merged into the
profile. BoundedContext can be inspected for the paused review or used after
acceptance. Its contents are untrusted data, never system instructions or grants.
No provider is connected to this context in Phase 7.

- Input history: at most 100 messages, each at most 16,000 characters.
- Output history: the newest at most 8 messages; each user/assistant/tool payload
  at most 2,048 UTF-8 bytes and combined text at most 8,192 bytes.
- UTF-8-safe truncation is labeled. Omitted/truncated counts form a deterministic
  non-authoritative summary; no invented semantic summary or permanent chat log.
- Memory selection: at most 20 records, combined serialized size 24,000 bytes;
  oversized selection fails explicitly instead of truncating confirmed facts.
- Profile context: at most 20 confirmed facts and 16,000 serialized bytes; size
  omissions are reported. Stable IDs/evidence remain attached to included facts.
- State history views include only bounded references and status. Existing Phase 5
  tools retain their result/payload limits; external network adapters remain deferred.

## Storage, concurrency and verified limits

The memory DB uses its own application identifier and schema version 1. It refuses
unrecognized databases. The checkpoint helper rejects business/memory files,
including supplied hard-link aliases; use a separate checkpoint path. Existing
business schema v2 and serialized aggregates are unchanged. Initialization is
explicit; no new database is opened by import or the health command. No migration
from business tables into memory is automatic. Unknown schemas fail without overwrite.

Official SqliteSaver owns checkpoint tables/WAL setup. Its connection is closed by
our context manager. The serializer disables pickle fallback and explicitly restricts
msgpack extensions; state uses primitive values only. InMemorySaver uses the same
serializer and is for isolated tests, not restart durability. LangSmith tracing is
disabled around graph operations, including when ambient tracing is enabled.

Short operations acquire a BEGIN IMMEDIATE reservation on the memory/registry DB,
serializing same-thread operations across independent graph/saver instances. No
model/network call belongs under this lock. SQLite releases the reservation on
process exit; busy waits expire after five seconds with a surfaced storage error.
The memory and checkpoint files are not one atomic distributed transaction;
commit ordering and tombstones keep failed deletes/starts inaccessible. Keep the
registry paired with its checkpoint file and back them up consistently.

Tests verify reopening all resources, abrupt process exit after a synchronous
pause and resuming in a new process, state/history, cross-user denial on every
operation, concurrent resume through different connections and optimistic memory
updates, memory deletion/context invalidation, purge failure/retry and trimming.
This demonstrates local restart recovery under those scenarios, not production
HA, power-loss recovery, network-filesystem behavior, high-contention scalability,
encryption, cross-machine concurrency or recovery from arbitrary disk corruption.

## Dependencies and official references

No existing package was upgraded. The added official adapter locks
langgraph-checkpoint-sqlite 3.1.2, with aiosqlite 0.22.1 and sqlite-vec 0.1.9
transitively. Async/vector APIs are not used. Existing LangGraph 1.2.18 and
langgraph-checkpoint 4.3.1 remain locked. Installed signatures/source were inspected
for SqliteSaver, serializer configuration, deletion, StateGraph durability,
StateSnapshot and interrupt/Command behavior, then exercised in tests.

- [Official persistence guide](https://docs.langchain.com/oss/python/langgraph/persistence)
- [Official interrupt/resume guide](https://docs.langchain.com/oss/python/langgraph/interrupts)
- [Official memory guide](https://docs.langchain.com/oss/python/langgraph/add-memory)
- [LangGraph 1.2.18 types source](https://github.com/langchain-ai/langgraph/blob/1.2.18/libs/langgraph/langgraph/types.py)
- [Official SQLite package and security guidance](https://pypi.org/project/langgraph-checkpoint-sqlite/)

Current online guides contain newer APIs as well; this implementation deliberately
uses the signatures tested against the installed locked versions.
